Status: DRAFT for the pilot, published with the code as DESIGN_2028 section 3.8 requires. Nothing here has been red-teamed yet (see `docs/RELEASE_GATE.md`, `docs/RED_TEAM_SCOPE.md`).

Markers used in this document:

- **BUILT**: implemented and covered by a test named in the traceability table.
- **PARTIAL**: implemented, but with a stated gap (untested, in-memory, depends on configuration, or weaker than the design asks).
- **DEV-ONLY**: the code path exists but only a development stand-in is installed; production startup refuses it (`server/civic/guards.ts`).
- **NOT BUILT**: nothing in the repository implements it. Also written **[PLAN]**.
- **[VERIFY]**: needs counsel or an independent reviewer.

A claim without a row in section 4A is not a claim this document makes. `tests/gate/traceability.test.ts` fails if a file or test tag cited in that table does not exist, or a line number is past the end of its file. It cannot check that the cited code still does what the row says; that is what the reviewer of RELEASE_GATE row 1 is for.

## 1. What this system is and is not

A civic participation platform: verified residents report local issues, track them, and (later) answer issue/service surveys. It is **not** an election, and it publishes no vote forecast. Phase 1 runs behind development stand-ins for every external provider: no real SMS provider, no HSM/KMS, no real number-intelligence vendor, no real device attestation, no real telecom aggregator. The controls below describe the target and the current state. The provider interfaces are the seams where real adapters plug in; another work stream is writing vendor adapters, and until one is installed and listed in section 4A as BUILT the row stays DEV-ONLY.

## 2. Assets

| Asset | Why it matters |
|---|---|
| Phone number to person link | Re-identification, harassment, targeting |
| PIN hashes, session tokens, OTP secrets | Account takeover |
| Residence and household data | Location privacy; small-village re-identification |
| Issue reports (text, voice notes, village) | May name individuals; may expose reporters |
| Survey responses (later phases) and the "has responded" flag | Secrecy of opinion; coercion |
| Audit log | Proof of what operators and officers did |
| Keys (pepper, signing, encryption) | Root of every other control |
| Published aggregates and issue metrics | Public trust; manipulation target |
| Sender identity and notification channel (later phases) | Phishing and false emergency messages |

## 3. Adversaries

Political parties and paid crowds; organised cadres with real phones; insiders (officers, volunteers, admins); sender-account hijackers; DDoS and booter services; the operator itself under pressure; state-level actors.

## 5. What secrecy does NOT guarantee

Read this before relying on any claim of anonymity.

1. **Not cryptographic ballot secrecy.** Even in later survey phases, "has responded" lives with the identity service and answers in a separate store with coarse strata only. This reduces linkage; it does not make linkage impossible. Whoever controls both stores plus the keys, or a court-ordered or coerced operator, may be able to rejoin them.
2. **Small groups re-identify people.** In a small village, a combination of village, age band and gender can point to one person. Minimum cell sizes (30) and roll-up reduce this but cannot remove it, and issue reports with free text or voice can identify the reporter by content alone.
3. **Network and telecom observers see metadata.** The SMS provider, telecom and IVR aggregator see that a number sent or received a message or call, and when. Voice notes carry the speaker's voice. Missed-call and IVR channels run over operators we do not control.
4. **Phones are not trusted.** A shared phone, a family member watching, coercion at home, or a stolen unlocked device defeats any app-level secrecy. A household head cannot see members' answers by design, but can see the roster and can pressure members. The IVR personal PIN stops a family member who does not know it; it does not stop one who does.
5. **Number recycling and SIM swap.** A recycled or swapped number can receive OTPs; flags and age gates reduce the risk, they do not remove it, and the flag source is a development fixture today (T-02).
6. **Dev providers are not production.** Dev OTP exposure (`CIVIC_EXPOSE_DEV_OTP=1`), the env-derived dev key, the console SMS provider, the fixture number-intelligence list and the dev attestation token provide no real protection. Production startup refuses to run on them (T-22), which means a real deployment cannot start until real adapters are installed.
7. **The operator is a trusted party until controls are real.** Until HSM/KMS, dual control and external audit anchoring with an independent witness exist, a malicious operator or admin with server access can read or alter data. The four stores share a host, a volume and one key provider.
8. **Audit logs prove order, not truth.** A hash chain without an anchor the operator cannot rewrite can be rebuilt by whoever holds the database and the audit key. The anchor sinks exist, but a sink only helps if it is configured and independent (T-27).
9. **Legal compulsion.** Law-enforcement and court-order access is a policy question **[VERIFY]**; technical controls do not override it.
10. **The pilot is a signal, not a representative sample.** Phone ownership, gender and age skew who participates; results must carry that caveat. Electoral-roll marginals are not available to check the skew against; Census 2011 provides sex (and SC/ST) marginals only (`docs/PILOT_SKEW_PLAN.md`).
